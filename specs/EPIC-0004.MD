# Epic 3: Machine Learning

## Objective

Introduce a machine learning ranking model that can replace or complement the rule-based scorer.

The ML system should learn from:

- External restaurant rating dataset
- First-party recommendation feedback
- User preferences
- Restaurant features

The goal is not to discover restaurants. The goal is to score candidate restaurants already selected by the Recommendation Engine.

---

# SPEC-012: Training Dataset Pipeline

## Goal

Build a repeatable pipeline that converts raw data into ML-ready training datasets.

## Scope

### In Scope

- External dataset ingestion
- First-party interaction export
- Label generation
- Feature generation
- Dataset versioning
- Train/validation/test split

### Out of Scope

- Model training
- Model serving
- Recommendation API changes

---

Used once the app has enough user activity.

---

## Label Generation

External ratings:

```text
Rating >= 4 → positive label = 1
Rating <= 2 → negative label = 0
Rating = 3  → ignored for MVP
```

First-party feedback:

```text
LIKE → positive label = 1
DISLIKE → negative label = 0
Rating >= 4 → positive label = 1
Rating <= 2 → negative label = 0
Rating = 3 → ignored for MVP
```

---

## Dataset Row Shape

Each row represents:

```text
User/Profile Context + Restaurant Candidate → Label
```

Example:

```json
{
  "userFeatures": {
    "favoriteCuisines": ["japanese"],
    "preferredAmbiance": ["casual"],
    "budgetLevel": 2
  },
  "restaurantFeatures": {
    "priceLevel": 2,
    "rating": 4.7,
    "ratingCount": 1200,

    "ambianceMatch": 0.7
  },
  "contextFeatures": {
    "dayOfWeek": "friday",
    "timeOfDay": "dinner"
  },

}
```

# SPEC-013: TensorFlow Training

## Goal

Train a ranking model that predicts the likelihood of positive user feedback for a restaurant candidate.

## Scope

### In Scope

- TensorFlow model definition
- Training loop
- Evaluation
- Model artifact export
- Model registry metadata

### Out of Scope

- Online inference API
- Recommendation business rules
- Google Places integration

---

## Model Responsibility

The model receives:

```text
User Features + Restaurant Features + Context Features
```

and returns:

```text
Recommendation Score
```

The model does not:

- Fetch restaurants
- Apply location filters
- Choose hero/secondary recommendations
- Persist sessions
- Apply business rules

---

## Initial Model Architecture

Use a simple dense ranking model.

```text
User Feature Vector
Restaurant Feature Vector
Context Feature Vector
        ↓
Concatenate
        ↓
Dense Layer
        ↓
Dense Layer
        ↓
Sigmoid Output
        ↓
Score 0.0 - 1.0
```

## Loss Function

```text
Binary Cross Entropy
```

## Metrics

Track:

```text
AUC
Precision
Recall
Accuracy
Precision@5
NDCG@5
```

Business comparison later happens inside the app using recommendation sessions.

---

## Model Artifact

Export model with:

```text
model_name
model_version
feature_version
dataset_version
metrics
created_at
```

Example:

```text
restaurant_ranker_v1
```

---

## Model Registry

Model metadata should be stored in Postgres:

```sql
ml_models (
  id uuid primary key,
  model_name text not null,
  version text not null,
  feature_version text not null,
  training_dataset_version text,
  metrics jsonb,
  artifact_uri text,
  deployed_at timestamp,
  created_at timestamp not null
);
```

---

## Acceptance Criteria

- Model trains from dataset pipeline output.
- Model produces normalized scores.
- Model artifact is exported.
- Metrics are recorded.
- Model metadata is registered.
- Model can be evaluated against the rule-based baseline.

# SPEC-014: Prediction Service

## Goal

Expose the trained model through the Python prediction service.

## Scope

### In Scope

- Model loading
- Prediction endpoint
- Batch scoring
- Version reporting
- Health check
- Error handling

### Out of Scope

- Candidate generation
- Business rules
- Session persistence
- User feedback collection

---

## API Endpoints

### Health Check

```http
GET /health
```

Response:

```json
{
  "status": "ok",
  "modelLoaded": true,
  "modelVersion": "restaurant_ranker_v1",
  "featureVersion": "restaurant_recommendation_v1"
}
```

### Predict

```http
POST /predict
```

Request:

```json
{
  "modelVersion": "restaurant_ranker_v1",
  "featureVersion": "restaurant_recommendation_v1",
  "userFeatures": {},
  "contextFeatures": {},
  "restaurantFeatures": [
    {
      "restaurantId": "uuid",
      "features": {}
    }
  ]
}
```

Response:

```json
{
  "modelVersion": "restaurant_ranker_v1",
  "scores": [
    {
      "restaurantId": "uuid",
      "score": 0.91
    }
  ]
}
```

---

## NestJS Integration

NestJS should call the Prediction Service only through a scorer implementation:

```ts
class TensorFlowScorer implements RecommendationScorer {
  score(input: RecommendationScoringInput): Promise<ScoredRestaurant[]> {
    // calls Python /predict
  }
}
```

The Recommendation Engine should not know whether the score came from rules or TensorFlow.

---

## Fallback Behavior

If Python prediction fails:

```text
Fallback to RuleBasedScorer
```

The request should still return recommendations.

The failure should be logged with:

```text
session_id
user_id
model_version
feature_version
error
```

---

## Acceptance Criteria

- Prediction service loads model.
- Health endpoint reports loaded model and version.
- Predict endpoint supports batch restaurant scoring.
- NestJS can use TensorFlowScorer.
- Failures fall back to rule-based scoring.
- Recommendation sessions store model version when ML is used.

Epic 3 is complete when:

- Training dataset can be generated.
- TensorFlow model can be trained.
- Model metrics are recorded.
- Model artifact is versioned.
- Python service can serve predictions.

---

# Suggested Implementation Order

1. Build external dataset ingestion.
2. Build first-party dataset export.
3. Implement dataset label generation.
4. Connect Feature Store output to dataset generation.
5. Train first TensorFlow ranking model.
6. Register model metadata in Postgres.
7. Implement Python `/health`.
8. Implement Python `/predict`.
9. Implement `TensorFlowScorer` in NestJS.
10. Run shadow predictions beside the rule-based scorer.
11. Compare ML scores against rule-based baseline.
12. Enable ML scorer only after it performs better than the baseline.

---

# ML Readiness Checklist

Before using ML in production recommendations:

- Rule-based scorer is already collecting baseline metrics.
- Feedback events are reliably stored.
- Feature versioning is stable.
- Dataset generation is reproducible.
- Offline metrics are acceptable.
- Shadow testing has run without impacting users.
- ML latency is acceptable.
- Rule-based fallback works.
- Model version is stored in recommendation sessions.
