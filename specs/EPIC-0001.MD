# Epic 0: Recommendation Platform Foundation

## Objective

Build the foundational backend capabilities required for the restaurant recommendation system.

This epic establishes:

- The recommendation domain model
- Google Places integration
- Local restaurant persistence
- Restaurant synchronization strategy
- Shared contracts used by the recommendation engine

This epic does **not** include recommendation scoring, ML, user feedback learning, or ranking logic. Those are handled in later epics.

---

# SPEC-000: Recommendation Architecture & Shared Contracts

## Goal

Define the shared contracts, enums, and abstractions used across the recommendation platform.

## Scope

### In Scope

- Shared TypeScript interfaces
- Provider abstractions
- Recommendation strategy enums
- Interaction type enums
- Feature/version identifiers
- Error conventions
- Common value objects

### Out of Scope

- Database implementation
- Google Places API calls
- Recommendation scoring
- ML model integration

## Core Interfaces

```ts
interface Location {
  latitude: number;
  longitude: number;
}

interface RestaurantCandidate {
  provider: 'GOOGLE_PLACES';
  providerPlaceId: string;
  name: string;
  location: Location;
  types: string[];
  primaryType?: string;
  priceLevel?: number;
  rating?: number;
  ratingCount?: number;
  businessStatus?: string;
  openNow?: boolean;
}

interface PlacesProvider {
  searchNearby(input: NearbySearchInput): Promise<RestaurantCandidate[]>;
  getPlaceDetails(providerPlaceId: string): Promise<RestaurantDetails>;
}
```

## Core Enums

```ts
enum RecommendationStrategy {
  PopularNearby = 'POPULAR_NEARBY',
  RuleBasedV1 = 'RULE_BASED_V1',
  TensorFlowV1 = 'TENSORFLOW_V1',
}

enum RecommendationInteractionType {
  Like = 'LIKE',
  Dislike = 'DISLIKE',
  Rating = 'RATING',
  Ignored = 'IGNORED',
}

enum RestaurantProvider {
  GooglePlaces = 'GOOGLE_PLACES',
}
```

## Acceptance Criteria

- Shared contracts are defined in a dedicated recommendation module.
- Contracts are provider-agnostic where possible.
- Google-specific fields are isolated behind provider mapping.
- Later specs can depend on these interfaces without redefining them.

# SPEC-001: Recommendation Domain Model

## Goal

Create the database schema required to support restaurant recommendations, sessions, feedback, and future ML training.

## Scope

### In Scope

- Restaurant tables
- User preference tables
- Recommendation session tables
- Recommendation result tables
- Interaction tables
- Model metadata table
- Indexing strategy

### Out of Scope

- Actual recommendation generation
- Google Places API integration
- TensorFlow model training

---

## Proposed Tables

### restaurants

Stores restaurants discovered through Google Places.

```sql
restaurants (
  id uuid primary key,
  provider text not null,
  provider_place_id text not null,
  name text not null,
  latitude decimal not null,
  longitude decimal not null,
  primary_type text,
  types text[],
  price_level integer,
  google_rating decimal,
  google_rating_count integer,
  business_status text,
  website text,
  phone text,
  editorial_summary text,
  first_seen_at timestamp not null,
  last_seen_at timestamp not null,
  last_synced_at timestamp,
  created_at timestamp not null,
  updated_at timestamp not null,

  unique(provider, provider_place_id)
);
```

### user_preferences

Stores explicit onboarding preferences.

```sql
user_preferences (
  id uuid primary key,
  user_id uuid not null,
  favorite_cuisines text[],
  preferred_ambiance text[],
  budget_level integer,
  created_at timestamp not null,
  updated_at timestamp not null,

  unique(user_id)
);
```

### user_profiles

Stores learned preference signals.

```sql
user_profiles (
  id uuid primary key,
  user_id uuid not null,
  profile_version text not null,
  cuisine_affinities jsonb,
  ambiance_affinities jsonb,
  budget_affinity jsonb,
  updated_at timestamp not null,

  unique(user_id)
);
```

### recommendation_sessions

Represents one recommendation experience.

```sql
recommendation_sessions (
  id uuid primary key,
  user_id uuid not null,
  latitude decimal not null,
  longitude decimal not null,
  radius_meters integer not null,
  strategy text not null,
  model_version text,
  feature_version text not null,
  candidate_count integer not null,
  generated_at timestamp not null
);
```

### recommendations

Stores each restaurant shown in a session.

```sql
recommendations (
  id uuid primary key,
  session_id uuid not null references recommendation_sessions(id),
  restaurant_id uuid not null references restaurants(id),
  position integer not null,
  score decimal not null,
  is_primary boolean not null default false,
  created_at timestamp not null
);
```

### recommendation_interactions

Stores user interactions as immutable events.

```sql
recommendation_interactions (
  id uuid primary key,
  recommendation_id uuid not null references recommendations(id),
  user_id uuid not null,
  interaction_type text not null,
  value jsonb,
  created_at timestamp not null
);
```

### restaurant_ratings

Stores explicit restaurant ratings.

```sql
restaurant_ratings (
  id uuid primary key,
  user_id uuid not null,
  restaurant_id uuid not null references restaurants(id),
  rating integer not null,
  comment text,
  created_at timestamp not null,
  updated_at timestamp not null
);
```

### ml_models

Tracks deployed ML models.

```sql
ml_models (
  id uuid primary key,
  model_name text not null,
  version text not null,
  feature_version text not null,
  training_dataset_version text,
  metrics jsonb,
  deployed_at timestamp,
  created_at timestamp not null,

  unique(model_name, version)
);
```

## Index Strategy

Recommended indexes:

```sql
create index idx_restaurants_provider_place_id
  on restaurants(provider, provider_place_id);

create index idx_restaurants_location
  on restaurants(latitude, longitude);

create index idx_recommendation_sessions_user
  on recommendation_sessions(user_id, generated_at desc);

create index idx_recommendations_session
  on recommendations(session_id);

create index idx_interactions_user
  on recommendation_interactions(user_id, created_at desc);

create index idx_ratings_restaurant
  on restaurant_ratings(restaurant_id);
```

## Acceptance Criteria

- All required tables are created.
- Restaurants are uniquely identified by provider + provider place ID.
- Recommendation sessions are immutable.
- User interactions are stored as events.
- Schema supports both rule-based and future ML recommendations.

# SPEC-002: Google Places Integration

## Goal

Integrate Google Places as the initial restaurant discovery provider.

Google Places is used for discovery, not as the permanent recommendation source of truth.

## Scope

### In Scope

- Places Provider abstraction
- Google Places implementation
- Nearby Search
- Optional Place Details
- Field masks
- Response mapping
- Error handling
- API key configuration

### Out of Scope

- Recommendation ranking
- Feature Store
- ML scoring

---

## Provider Contract

```ts
interface NearbySearchInput {
  location: Location;
  radiusMeters: number;
  maxResultCount?: number;
  includedTypes?: string[];
}

interface PlacesProvider {
  searchNearby(input: NearbySearchInput): Promise<RestaurantCandidate[]>;
  getPlaceDetails(providerPlaceId: string): Promise<RestaurantDetails>;
}
```

## Nearby Search Request

Use Google Places Nearby Search for candidate discovery.

Endpoint:

```http
POST https://places.googleapis.com/v1/places:searchNearby
```

Request body:

```json
{
  "includedTypes": ["restaurant"],
  "maxResultCount": 100,
  "locationRestriction": {
    "circle": {
      "center": {
        "latitude": -22.9068,
        "longitude": -47.0626
      },
      "radius": 5000
    }
  }
}
```

Recommended field mask:

```text
places.id,
places.displayName,
places.location,
places.primaryType,
places.types,
places.priceLevel,
places.rating,
places.userRatingCount,
places.businessStatus
```

## Data Mapping

Google field → Internal field:

```text
places.id -> provider_place_id
places.displayName.text -> name
places.location.latitude -> latitude
places.location.longitude -> longitude
places.primaryType -> primary_type
places.types -> types
places.priceLevel -> price_level
places.rating -> google_rating
places.userRatingCount -> google_rating_count
places.businessStatus -> business_status
```

## Error Handling

The provider should handle:

- Invalid API key
- Rate limit errors
- Empty results
- Network errors
- Google API validation errors
- Partial/missing fields

Failures should not crash the recommendation flow. The service should return a controlled application error.

## Acceptance Criteria

- Backend can fetch nearby restaurants from Google Places.
- Results are mapped to internal `RestaurantCandidate` objects.
- API key is read from environment configuration.
- Field mask avoids unnecessary expensive data.
- Provider is abstracted behind `PlacesProvider`.

# SPEC-003: Restaurant Synchronization

## Goal

Persist and maintain restaurants discovered through Google Places.

The database acts as a knowledge cache, while Google Places remains the discovery source of truth.

## Scope

### In Scope

- Upsert strategy
- Mutable vs internal fields
- First-seen and last-seen tracking
- Sync during recommendation requests
- Optional background refresh

### Out of Scope

- Ranking
- Feedback learning
- ML features

---

## Synchronization Philosophy

Google Places answers:

> What restaurants exist near this user right now?

Our database answers:

> What have we learned about these restaurants over time?

Therefore:

- Always use Google Places for nearby discovery.
- Always persist discovered restaurants.
- Always enrich Google results with internal data before recommending.
- Never overwrite internal application data with Google data.

---

## Request-Time Sync Flow

```text
User requests recommendations
  ↓
Google Places Nearby Search
  ↓
Map results to RestaurantCandidate[]
  ↓
Upsert restaurants into PostgreSQL
  ↓
Load enriched restaurant records
  ↓
Pass to candidate generation/recommendation pipeline
```

## Upsert Rules

Match by:

```text
provider + provider_place_id
```

If restaurant does not exist:

- Insert new restaurant
- Set `first_seen_at`
- Set `last_seen_at`
- Set `last_synced_at`

If restaurant exists:

- Update mutable Google-owned fields
- Update `last_seen_at`
- Update `last_synced_at`
- Preserve internal fields

## Google-Owned Fields

Safe to update from Google:

- name
- latitude
- longitude
- primary type
- types
- price level
- Google rating
- Google rating count
- business status
- open now
- website
- phone
- editorial summary

## App-Owned Fields

Must not be overwritten by Google:

- recommendation count
- like count
- dislike count
- internal ratings
- feature vectors
- embeddings
- last recommended timestamp
- learned popularity scores

## Background Refresh

A background job may refresh restaurants that:

- were recommended recently
- were liked or rated by users
- are frequently shown
- have stale `last_synced_at`

Initial recommendation:

```text
Refresh popular/recent restaurants every 24 hours.
```

## Acceptance Criteria

- Google results are upserted before recommendation generation.
- New restaurants can be recommended immediately.
- Existing restaurants retain internal data.
- Sync logic is idempotent.
- Duplicate restaurants are avoided through provider + provider place ID uniqueness.
