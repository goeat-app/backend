# Epic 4: Platform Operations

## Objective

Add the operational layer needed to monitor, maintain, and safely evolve the recommendation system.

This epic is mostly owned by the **Node/NestJS backend**, with optional Python involvement later for ML-specific jobs.

---

# SPEC-016: Monitoring & Analytics

## Owner

**Node/NestJS**

## Goal

Track recommendation quality, system health, and user behavior.

## Metrics to Track

### Recommendation Metrics

- Recommendation sessions created
- Hero recommendation acceptance rate
- Secondary recommendation acceptance rate
- Like/dislike ratio
- Refresh rate
- Average candidate count
- Average score of selected recommendations
- Number of recommendations returned per session

### User Behavior Metrics

- Users with preferences completed
- Users who requested recommendations
- Users who gave feedback
- Users who rated restaurants
- Repeat recommendation usage

### System Metrics

- Google Places latency
- Google Places error rate
- Candidate generation latency
- Feature Store latency
- Scoring latency
- Recommendation API latency
- Database query latency

## Required Logs

Each recommendation request should log:

```text
user_id
session_id
strategy
feature_version
candidate_count
selected_count
radius_meters
google_places_latency_ms
scoring_latency_ms
total_latency_ms
```

## Acceptance Criteria

- Recommendation requests are observable.
- Candidate counts and selected restaurants are logged.
- Feedback events are measurable.
- Google Places failures are tracked.
- Recommendation quality can be analyzed over time.

# SPEC-017: Background Jobs

## Owner

**Node/NestJS**

## Goal

Run asynchronous maintenance tasks that keep recommendation data fresh and useful.

## Jobs

### Restaurant Refresh Job

Refresh restaurants that are:

- Recently recommended
- Recently liked
- Recently rated
- Frequently shown
- Stale according to `last_synced_at`

Recommended cadence:

```text
Every 24 hours
```

### User Profile Recompute Job

Rebuild learned user profiles from interaction history.

Recommended cadence:

```text
Daily
```

This prevents profile drift caused by incremental updates.

### Feature Recompute Job

Recompute feature vectors when:

- Feature version changes
- Restaurant data changes
- User profile changes

### Recommendation Cleanup Job

Optional.

Archive or mark old recommendation sessions for analytics/storage management.

## Acceptance Criteria

- Background jobs can run independently from API requests.
- Failed jobs are logged.
- Jobs are idempotent.
- Restaurant refresh does not overwrite app-owned data.
- User profile recomputation matches interaction history.

# SPEC-018: Strategy Configuration

## Owner

**Node/NestJS**

## Goal

Make recommendation behavior configurable without changing code.

## Configurable Values

### Candidate Generation

```json
{
  "defaultRadiusMeters": 5000,
  "maxRadiusMeters": 12000,
  "minimumCandidates": 20,
  "idealCandidates": 50
}
```

### Rule-Based Scoring

```json
{
  "cuisineMatchWeight": 0.35,
  "budgetMatchWeight": 0.25,
  "ambianceMatchWeight": 0.2,
  "ratingWeight": 0.1,
  "distanceWeight": 0.1
}
```

### Business Rules

```json
{
  "heroCount": 1,
  "secondaryCount": 4,
  "recentlyShownSuppressionHours": 24,
  "minimumCuisineDiversity": 2
}
```

## Acceptance Criteria

- Recommendation weights are configurable.
- Radius and candidate limits are configurable.
- Business rules are configurable.
- Config values are versioned or logged in recommendation sessions.

# SPEC-019: Failure Handling & Fallbacks

## Owner

**Node/NestJS**

## Goal

Ensure the recommendation API can still return useful results when part of the system fails.

## Failure Scenarios

### Google Places Unavailable

Fallback:

```text
Use recently cached restaurants near the user if available.
```

### Not Enough Candidates

Fallback:

```text
Expand radius.
Relax recently-shown suppression.
Relax cuisine matching.
Return fewer recommendations if needed.
```

### User Has No Preferences

Fallback:

```text
Use popular nearby restaurants ranked by rating, rating count, distance, and open status.
```

### Feature Store Failure

Fallback:

```text
Use minimal restaurant fields and popular nearby scoring.
```

### Scorer Failure

Fallback:

```text
Use PopularNearbyScorer.
```

## Acceptance Criteria

- Recommendation API does not hard-fail for common issues.
- Fallback strategy is stored in the recommendation session.
- Fallback usage is logged.
- Client receives a controlled response.

# SPEC-020: Admin / Debug Tooling

## Owner

**Node/NestJS**

## Goal

Provide internal visibility into why recommendations were generated.

## Debug Capabilities

For a given recommendation session, show:

- User preferences used
- Candidate count
- Filtered-out candidates
- Feature version
- Strategy
- Scores
- Score breakdown
- Business rules applied
- Final ranking

## Optional Endpoint

```http
GET /admin/recommendation-sessions/{sessionId}
```

## Acceptance Criteria

- Engineers can debug bad recommendations.
- Score breakdowns are visible.
- Business rule decisions are inspectable.
- Debug endpoints are protected/admin-only.

---

# Epic 4 Completion Criteria

Epic 4 is complete when:

- Recommendation quality is measurable.
- Background maintenance jobs are running.
- Recommendation configuration can be changed safely.
- Common failure cases have fallback behavior.
- Engineers can inspect recommendation sessions for debugging.
