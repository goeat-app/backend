# Epic 2: User Learning

## Objective

Capture user preferences and feedback so the recommendation system can improve over time.

This epic turns the MVP recommendation engine from a static rule-based experience into a personalized system that learns from each user independently.

The initial scope remains simple:

- Store onboarding preferences
- Capture thumbs up/down feedback
- Capture restaurant ratings
- Update user profile signals
- Use learned preferences in future recommendation requests

This epic does **not** include collaborative filtering, global trending, or TensorFlow training. Those come later.

---

# SPEC-009: User Preferences

## Goal

Store explicit user preferences collected during onboarding.

These preferences are the starting point for cold-start recommendations.

## Scope

### In Scope

- Favorite cuisines
- Preferred ambiance
- Budget level
- Preference updates
- Preference retrieval for recommendation requests

### Out of Scope

- Learned profile evolution
- ML model training
- Social recommendations

---

## Data Model

```sql
user_preferences (
  id uuid primary key,
  user_id uuid not null unique,
  favorite_cuisines text[] not null default '{}',
  preferred_ambiance text[] not null default '{}',
  budget_level integer,
  created_at timestamp not null,
  updated_at timestamp not null
);
```

## API

### Upsert User Preferences

```http
PUT /users/me/preferences
```

Request:

```json
{
  "favoriteCuisines": ["japanese", "italian"],
  "preferredAmbiance": ["casual", "romantic"],
  "budgetLevel": 2
}
```

### Get User Preferences

```http
GET /users/me/preferences
```

Response:

```json
{
  "favoriteCuisines": ["japanese", "italian"],
  "preferredAmbiance": ["casual", "romantic"],
  "budgetLevel": 2
}
```

## Validation

- `favoriteCuisines` must be a known cuisine list or normalized free-text.
- `preferredAmbiance` must be one of the supported ambiance tags.
- `budgetLevel` should map to the app’s supported price levels.

## Acceptance Criteria

- User preferences can be created and updated.
- Recommendation engine can load user preferences.
- Preferences are used by Feature Store v1.
- Missing preferences do not break recommendations.

# SPEC-010: Feedback Collection

## Goal

Capture user interactions with recommendations.

Feedback is stored as immutable events and later used to update user profiles and train ML models.

## Scope

### In Scope

- Thumbs up
- Thumbs down
- Restaurant rating
- Feedback validation
- Interaction persistence
- Idempotency handling

### Out of Scope

- ML retraining
- Global popularity/trending
- Social recommendations

---

## Interaction Types

```ts
enum RecommendationInteractionType {
  Like = 'LIKE',
  Dislike = 'DISLIKE',
  Rating = 'RATING',
}
```

Future interaction types:

```ts
enum FutureInteractionType {
  Ignored = 'IGNORED',
  OpenedDetails = 'OPENED_DETAILS',
  Navigated = 'NAVIGATED',
  Visited = 'VISITED',
  Shared = 'SHARED',
}
```

---

## Feedback API

```http
POST /recommendations/{recommendationId}/feedback
```

Request examples:

### Like

```json
{
  "type": "LIKE"
}
```

### Dislike

```json
{
  "type": "DISLIKE"
}
```

### Rating

```json
{
  "type": "RATING",
  "rating": 5
}
```

## Backend Flow

```text
Receive feedback
  ↓
Validate recommendation exists
  ↓
Validate recommendation belongs to user
  ↓
Persist interaction event
  ↓
If rating, upsert restaurant rating
  ↓
Trigger user profile update
  ↓
Return success
```

## Data Model

### recommendation_interactions

```sql
recommendation_interactions (
  id uuid primary key,
  recommendation_id uuid not null references recommendations(id),
  user_id uuid not null,
  interaction_type text not null,
  value jsonb,
  created_at timestamp not null
);
```

### restaurant_ratings

```sql
restaurant_ratings (
  id uuid primary key,
  user_id uuid not null,
  restaurant_id uuid not null references restaurants(id),
  rating integer not null,
  comment text,
  created_at timestamp not null,
  updated_at timestamp not null,

  unique(user_id, restaurant_id)
);
```

## Idempotency / Duplicate Feedback

A user should not be able to accidentally create unlimited duplicate feedback for the same recommendation.

Recommended MVP behavior:

- One active LIKE/DISLIKE per recommendation per user.
- If user changes feedback, record a new event but treat latest as active state.
- Ratings should upsert per user + restaurant.

Optional helper table for current state:

```sql
recommendation_feedback_state (
  id uuid primary key,
  recommendation_id uuid not null,
  user_id uuid not null,
  current_type text not null,
  updated_at timestamp not null,

  unique(recommendation_id, user_id)
);
```

This keeps the event log immutable while making reads easier.

## Acceptance Criteria

- User can like a recommendation.
- User can dislike a recommendation.
- User can rate a restaurant.
- Feedback is tied to recommendation session history.
- Duplicate feedback is handled safely.
- Feedback can trigger user profile updates.

# SPEC-011: User Profile Evolution

## Goal

Update each user's learned preference profile based on their feedback.

This allows future recommendations to become more personalized over time without requiring a full ML model.

## Scope

### In Scope

- Cuisine affinity updates
- Ambiance affinity updates
- Budget affinity updates
- Positive/negative feedback weighting
- Profile recomputation strategy

### Out of Scope

- Collaborative filtering
- Global recommendation learning
- TensorFlow retraining

---

## Profile Concept

`user_preferences` stores what the user explicitly said.

`user_profiles` stores what the system has learned.

Example:

```json
{
  "cuisineAffinities": {
    "japanese": 0.85,
    "italian": 0.67,
    "burger": -0.25
  },
  "ambianceAffinities": {
    "casual": 0.72,
    "romantic": 0.31
  },
  "budgetAffinity": {
    "1": -0.1,
    "2": 0.75,
    "3": 0.2,
    "4": -0.4
  }
}
```

## Update Strategy

For MVP, use deterministic updates.

### Positive Feedback

LIKE or rating >= 4:

```text
Increase affinity for restaurant cuisine, ambiance, and budget.
```

### Negative Feedback

DISLIKE or rating <= 2:

```text
Decrease affinity for restaurant cuisine, ambiance, and budget.
```

### Neutral Feedback

Rating = 3:

```text
No strong update.
```

## Suggested Weights

```text
LIKE: +0.10
DISLIKE: -0.10
Rating 5: +0.15
Rating 4: +0.10
Rating 3: 0.00
Rating 2: -0.10
Rating 1: -0.15
```

Clamp affinity values between:

```text
-1.0 and 1.0
```

## Profile Update Flow

```text
Feedback event created
  ↓
Load recommendation
  ↓
Load restaurant features
  ↓
Apply affinity update
  ↓
Save user profile
```

## Recompute vs Incremental Update

MVP recommendation:

Use incremental updates immediately after feedback.

Future improvement:

Periodically recompute profile from the full interaction history to correct drift.

```text
Interaction history
  ↓
Recompute affinities
  ↓
Replace user_profile
```

## Feature Store Integration

The Feature Store should combine:

```text
Explicit preferences
+
Learned profile
```

Example:

```text
If user selected Japanese in onboarding: +base boost
If user also liked Japanese restaurants: +learned boost
If user disliked Japanese restaurants: reduce boost
```

## Acceptance Criteria

- User profile is created when first needed.
- Like/dislike updates learned affinities.
- Restaurant rating updates learned affinities.
- Feature Store uses learned profile data.
- Recommendations change over time based on feedback.

```text
User sees recommendations
  ↓

  ↓

```

- Users can dislike recommendations.

- Current feedback state is queryable.
- User profiles are updated from feedback.

3. Implement feedback endpoint.

5. Add current feedback state handling.
6. Add restaurant rating upsert.
7. Implement user profile update service.
8. Connect learned profile to Feature Store.
9. Add tests for profile evolution.
10. Validate that recommendations change after feedback.

---

# Important MVP Decision

Do not introduce global learning yet.

For Epic 2, learning should be **profile-independent**:

```text
User A feedback only affects User A.
```

Global learning/trending can be introduced later once interaction volume is high enough and analytics are reliable.
