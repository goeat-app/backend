# Epic 1: Recommendation Engine

## Objective

Build the first working recommendation engine using Google Places data, persisted restaurants, user preferences, deterministic feature generation, and a rule-based scoring strategy.

This epic delivers the MVP recommendation experience:

- One Hero Recommendation
- Four secondary options
- Personalized based on cuisine, ambiance, budget, distance, and quality
- No ML required yet
- Ready to be replaced by ML scoring later

---

# SPEC-004: Candidate Generation

## Goal

Generate a candidate pool of nearby restaurants that are eligible to be scored and recommended.

## Scope

### In Scope

- Load nearby restaurants from Google Places through the sync flow
- Use persisted/enriched restaurants from PostgreSQL
- Apply hard filters
- Produce a candidate list for scoring

### Out of Scope

- Ranking
- Feature scoring
- ML inference
- Final recommendation presentation

---

## Candidate Generation Flow

```text
User location
  ↓
Google Places Nearby Search
  ↓
Restaurant upsert
  ↓
Load enriched restaurants from DB
  ↓
Apply hard filters
  ↓
Candidate pool
```

## Hard Filters

Initial filters:

- Within search radius
- Business status is operational
- Open now, if available
- Has valid location
- Has minimum useful metadata
- Exclude restaurants recently disliked by the user
- Optionally exclude restaurants recommended too recently

## Radius Strategy

Initial default:

```text
radiusMeters = 5000
```

If the candidate count is too low, expand progressively:

```text
5km → 8km → 12km
```

Stop once enough candidates are found or the maximum radius is reached.

## Candidate Count

Target:

```text
Minimum candidates: 20
Ideal candidates: 50-100
```

If fewer than 5 candidates are available, return a fallback response rather than low-quality recommendations.

## Acceptance Criteria

- Candidate generation returns restaurants near the user.
- Google Places is used for discovery.
- Restaurants are persisted before being used.
- Hard filters are applied.
- The output is a clean list of candidates ready for feature generation.

## Feature Store Contract

```ts
interface FeatureStore {
  buildUserFeatures(userId: string): Promise<UserFeatureVector>;

  buildRestaurantFeatures(
```

Initial version:

```text
feature_version = restaurant_recommendation_v1
```

# SPEC-006: Recommendation Scoring

## Goal

Score candidate restaurants using a pluggable recommendation scorer.

The MVP uses a rule-based scorer. Future versions can replace it with TensorFlow without changing the recommendation pipeline.

## Scope

### In Scope

- RecommendationScorer interface
- RuleBasedScorer implementation
- Score normalization
- Configurable weights
- Scorer metadata

### Out of Scope

- ML model serving
- Final business rule selection
- Feedback learning

---

## Scorer Contract

```ts
interface RecommendationScorer {
  score(input: RecommendationScoringInput): Promise<ScoredRestaurant[]>;
}

interface RecommendationScoringInput {
  userFeatures: UserFeatureVector;
  restaurantFeatures: RestaurantFeatureVector[];
  contextFeatures: ContextFeatureVector;
}

interface ScoredRestaurant {
  restaurantId: string;
  score: number;
  scoreBreakdown?: Record<string, number>;
}
```

## Rule-Based Score Formula

Initial scoring:

```text
score =
  0.35 * cuisine_match
+ 0.25 * budget_match
+ 0.20 * ambiance_match
+ 0.10 * normalized_google_rating
+ 0.10 * normalized_distance
```

Weights should be configurable.

## Score Range

Scores must be normalized between:

```text
0.0 - 1.0
```

## Score Breakdown

The scorer should optionally return a breakdown for debugging:

```json
{
  "cuisineMatch": 0.35,
  "budgetMatch": 0.25,
  "ambianceMatch": 0.1,
  "rating": 0.08,
  "distance": 0.06
}
```

## Acceptance Criteria

- Candidates receive normalized scores.
- Rule-based scorer is implemented.
- Scoring weights are configurable.
- Scorer can be replaced without changing the recommendation service.
- Score breakdown is available for logs/debugging.

# SPEC-007: Business Rules Engine

## Goal

Transform scored restaurants into the final finite recommendation selection shown to the user.

## Scope

### In Scope

- Hero recommendation selection
- Secondary recommendation selection
- Diversity rules
- Recently shown suppression
- Tie-breaking
- Fallback handling

### Out of Scope

- Candidate discovery
- Scoring
- User feedback handling

---

## Output Shape

The engine should return:

```text
1 Hero Recommendation
4 Secondary Recommendations
```

Example:

```text
Today's Pick
- Restaurant A

Also worth considering
- Restaurant B
- Restaurant C
- Restaurant D
- Restaurant E
```

## Selection Rules

### Hero Recommendation

Choose the highest-scoring restaurant after suppression rules.

### Secondary Recommendations

Choose the next best restaurants while applying diversity.

Initial diversity rules:

- Avoid 5 restaurants with the same cuisine.
- Prefer at least 2 cuisine groups when available.
- Avoid showing the same restaurant too frequently.
- Avoid restaurants the user disliked.

### Recently Shown Suppression

Default:

```text
Do not show the same restaurant again within 24 hours
```

This can be relaxed if the candidate pool is too small.

### Tie-Breaking

When scores are similar, prefer:

1. Higher Google rating count
2. Shorter distance
3. Higher internal positive feedback
4. Random stable tie-breaker per session

## Acceptance Criteria

- Final result contains one hero and up to four secondary recommendations.
- Restaurants recently disliked are excluded.
- Recently shown restaurants are suppressed when possible.
- Result set has basic diversity.
- Rules are separate from scorer logic.

# SPEC-008: Recommendation Sessions

## Goal

Persist every recommendation experience as an immutable session.

This enables analytics, debugging, feedback attribution, A/B testing, and future ML training.

## Scope

### In Scope

- Create recommendation sessions
- Persist ranked recommendations
- Store strategy/model/feature versions
- Store scores and positions
- Expose recommendation history

### Out of Scope

- Feedback recording
- ML training
- User profile updates

---

## Session Creation Flow

```text
Final recommendations selected
  ↓
Create recommendation_session
  ↓
Create recommendation rows
  ↓
Return session + recommendations to client
```

## Stored Session Fields

Required:

- user_id
- latitude
- longitude
- radius_meters
- strategy
- model_version
- feature_version
- candidate_count
- generated_at

## Stored Recommendation Fields

Required:

- session_id
- restaurant_id
- position
- score
- is_primary
- score_breakdown, optional
- created_at

## History API

Initial endpoint:

```http
GET /recommendations/history
```

Returns recent sessions and the restaurants shown.

## Acceptance Criteria

- Each recommendation request creates a session.
- Recommendations are persisted with position and score.
- Sessions are immutable.
- History can be retrieved by user.
- Session stores strategy and feature version.

## Error Handling

Possible errors:

- Missing user preferences
- Invalid location
- No candidates found
- Google Places unavailable
- Scorer unavailable
- Database failure

Fallback behavior:

- If personalized scoring fails, use popular nearby strategy.
- If Google Places fails, optionally use recently cached restaurants nearby.
- If fewer than 5 restaurants are available, return fewer results with a warning.

## Acceptance Criteria

- Client can request recommendations.
- Client receives one hero and secondary options.
- Recommendation sessions are persisted.
- API handles low-candidate and provider-failure scenarios gracefully.

Epic 1 is complete when:

- A user can request recommendations from the app.
- Nearby restaurants are discovered and persisted.
- Candidate generation produces valid candidates.
- Feature Store v1 exists.
- Rule-based scoring is implemented.
- Business rules select one hero and secondary options.
- Recommendation sessions are persisted.
- The Recommendation API returns usable data to the client.

# MVP Notes

For the first MVP, do not introduce TensorFlow yet.

The rule-based scorer is not throwaway code. It is the production baseline.

Future ML work should only replace it if it improves:

- Recommendation acceptance rate
- Positive feedback rate
- Restaurant visit rate
- Refresh rate
- Decision completion rate
